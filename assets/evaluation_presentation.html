Executive summary

PowerCycles.jl is a Julia framework for steady-state gas-turbine cycle modeling built on a direct residual IR: component physics is declared as plain VariableSpec/ResidualRowSpec structs (the Residual IR), compiled to an integer-indexed ResidualProgram, and solved by NonlinearSolve.jl. The two-layer design keeps component code readable and test-friendly while delivering zero-allocation hot loops at solve time. v0.1 ships a CPG (calorically perfect gas) single-spool turbojet.

In a single session-day this went from an empty repository to a solving, spec-governed turbojet — and then was hardened past two problems that a less rigorous project would have buried: a real type-inference cliff found by a deliberate scalability probe, and eight ergonomics findings raised by an adversarial fresh-eyes audit. Both were fixed the same day and re-verified. Phase 7 (PyCycle cross-validation + ADR-0005 MTK memo) is now complete, with one gate miss characterized and its resolution path identified.

The architecture in one diagram

One pipeline carries a model from human-readable specs to a verified converged result. Each stage makes a specific guarantee; the named-error / determinism / sparsity-contract / zero-alloc / verified-convergence / actionable-failure promises are what make the framework trustworthy rather than merely working.

validate!

Six structured exceptions: DuplicateIDError (lists both owners), DanglingPortError, MissingDepsError, UnknownDerivSourceError, etc. The :unknown derivative tag constructs but never validates — silent gaps are rejected.

compile

Deterministic integer row/column maps in declared order. Kernels stored in a heterogeneous tuple, dispatched via @generated straight-line code (§5). jac_prototype = declared-dep union; optional verify_sparsity.

diagnose

Worst-first DiagnosticEntry table mapping a bad row back to its ID, owner, units, and touched variables — scaled residuals, so a 1e5-Pa row and a 1e-2 FAR row are comparable.

The math that matters

The CPG turbojet is a square 29-row system (physics doc §5 ledger). Four pieces of math carry the load; each maps 1:1 to a kernel in src/components/.

4.1 Two-gas FAR balance — and the enthalpy-reference subtlety

Under CPG, $h_{of\_T}(\text{gas}, T) = c_p\,T$ — enthalpy is measured from absolute zero with each gas's own $c_p$. The cold gas ($c_p=1004.5$) and hot gas ($c_p=1239.0$) therefore use different zero-references. The burner energy balance crosses this mismatch, so it is written deliberately: chemical release $\eta_b\,LHV$ is accounted explicitly rather than forming $h_{hot}-h_{cold}$ as if they shared a datum.

$$ FAR = \frac{c_{p,hot}\,T_{t4} - c_{p,cold}\,T_{t3}}{\eta_b\,LHV - c_{p,hot}\,T_{t4}} = \frac{h_{of\_T}(\text{HOT}, T_{t4}) - h_{of\_T}(\text{COLD}, T_{t3})}{\eta_b\,LHV - h_{of\_T}(\text{HOT}, T_{t4})} $$

src/components/burner.jl — R9 :burn_FAR (verbatim kernel)

push!(m, ResidualRowSpec(:burn_FAR; owner=owner, units=:ratio, scale=0.02,
    deps=[FAR_id, Tt_out_id, Tt_in_id], derivative=:forwarddiff,
    f=let hot=hot, cold=cold
        (d, p) -> begin
            h_hot  = h_of_T(hot,  d[2])
            h_cold = h_of_T(cold, d[3])
            d[1] * (p.eta_b * p.LHV - h_hot) - (h_hot - h_cold)
        end
    end))

Physics doc §2: "we do not form $h_{hot}-h_{cold}$ as if they shared a datum … this handles the reference mismatch by accounting chemical release explicitly rather than differencing two absolute enthalpies." This is the textbook (Mattingly) two-gamma result.

4.2 Where ηt enters — the inverse-isentropic map

The turbine pressure drop runs the isentropic map backwards: actual temperature ratio $\tau_t = T_{t5}/T_{t4}$ is converted to the ideal ratio via $\eta_t$ before the isentropic pressure relation is applied.

$$ \tau_{t,s} = 1 - \frac{1-\tau_t}{\eta_t}, \qquad P_{t5} = P_{t4}\,\mathrm{prftr}(\text{HOT}, \tau_{t,s}) $$

src/components/turbine.jl — R12 :turb_Pt (kernel, per physics doc §3.4)

f=(d, p) -> d[1] - d[2]*pressure_ratio_from_temperature_ratio(
                       HOT_GAS, 1 - (1 - d[3]/d[4])/p.eta_t)
#  d = [Pt5, Pt4, Tt5, Tt4]

4.3 Choked-nozzle branch — NPR 7.96 ≫ π* 1.832 — and ADR-0004 branch strategy

At the design point the nozzle pressure ratio $\text{NPR}=P_{t8}/P_0 \approx 7.96$ far exceeds the critical ratio $\approx 1.832$, so the convergent nozzle is choked: $M_8=1$, static exit pressure from the critical ratio, throat area from continuity. The branch is fixed at :choked_convergent and recorded in provenance — no mid-solve switching (PRD risk #3). The unchoked branch is documented but inactive.

$$ M_8 = 1,\quad P_8 = \frac{P_{t8}}{\mathrm{critical\_pressure\_ratio}(\text{HOT})},\quad \dot m_8 = \rho_8 V_8 A_8 $$

src/components/nozzle.jl — R18/R19 (verbatim)

push!(m, ResidualRowSpec(:noz_P8; ... deps=[P8_id, Pt8_id], ...
    f=let crit=critical_pressure_ratio(hot)
        (d, p) -> d[1] - d[2] / crit
    end))
push!(m, ResidualRowSpec(:noz_A8; ... deps=[mdot8_id, P8_id, Tt8_id, M8_id, A8_id], ...
    f=let hot=hot, Rhot=R(hot)
        (d, p) -> begin
            T8 = d[3] / Tt_over_T(hot, d[4])
            V8 = d[4] * speed_of_sound(hot, T8)
            ρ8 = d[2] / (Rhot * T8)
            d[1] - ρ8 * V8 * d[5]
        end
    end))

ADR-0004: branch selection for new problems

v0.1 asserts the branch a priori at construction (nozzle_mode=:choked_convergent), then post-solve checks NPR > π* ≈ 1.83 and errors loudly if violated — a model-definition error, not a silent wrong answer.

v0.2 plan (for off-design sweeps that cross the choking boundary): solve → check branch condition → switch nozzle_mode if violated → recompile (cheap, measured <0.05 s manifest recompile) → warm re-solve from previous iterate. Every switch is written to provenance metadata. The loop is bounded; a flip-flop at the same operating point (near NPR = π*) surfaces as an error, not infinite iteration. This is the NPSS-style discrete outer loop: residuals stay smooth and ForwardDiff-differentiable within each branch solve.

Three alternatives recorded as deferred in ADR-0004: smoothed blending (logistic on NPR − π*), complementarity/Fischer-Burmeister row, always-carry-both-branches with active-flag variable.

4.4 Per-row dual seeding for the Jacobian

Each row's partials are computed by ForwardDiff over only its N declared dep variables: an N-tuple of Dual seeds (1.0 in slot n, else 0.0), one kernel evaluation, partials scattered into the sparse $J$ at the declared $(i, \text{col})$ entries. N is a compile-time constant per tuple slot → type-stable, allocation-free.

src/compile/residual.jl — _jac_row! (verbatim)

@inline function _jac_row!(J, x, k, cols::NTuple{N,Int}, p, i) where {N}
    duals = _seed_duals(x, cols, Val(N))
    r = k(duals, p)
    parts = ForwardDiff.partials(r)
    @inbounds for n in 1:N
        J[i, cols[n]] = parts[n]
    end
    return nothing
end

The design-point solve uses 8 Newton iterations (nsteps 10, njacs 8 — one extra residual evaluation at the end). A cold solve_program call costs approximately 59 µs, decomposed as: ~24 µs one-time solver-cache initialization (NonlinearSolve.init) + ~17 µs Newton work (8 × (jacobian! ~0.79 µs + sparse LU factorization and back-solve + residual! ~0.13 µs)) + setup overhead. The warm-sweep API (init_solve builds the cache once; solve_program! re-solves via reinit!/solve!) eliminates the 24 µs init per point, yielding ~17 µs/point as the best-case minimum (tight-loop minimum; the fresh-process protocol of §6.3 measures a 54 µs median for the same call — the median is the number to quote when comparing across tools). Zero allocations in residual! and jacobian! after warmup on the full system.

src/compile/solve.jl — cost model docstring (verbatim)

-- Cost model (29-row turbojet, measured): a cold `solve_program` call is ≈ 60 µs,
-- of which ≈ 24 µs is one-time cache construction (`init`). A warm
-- `solve_program!` step on a pre-built cache is ≈ 17 µs — roughly the irreducible
-- Newton work (8 iters × (jacobian! + sparse LU + residual!)). So a sweep that
-- builds the cache once and reuses it per point is ~3× cheaper per point than
-- calling `solve_program` afresh.

5.2 Dense "Stalled" root-caused — not a wiring bug

Termination artifact diagnosed and fixed

The dense-Jacobian path reached the same root as the sparse path but reported Stalled instead of Success. Root cause: NonlinearSolve's default relative-norm termination criterion. On a multi-scale system (the turbojet mixes Pa, K, kg/s, dimensionless in a single vector), the final Newton increment is tiny but nonzero, so the relative criterion never trips and the solve exhausts its step cap and reports Stalled despite a machine-precision residual (~1e-10). The sparse path happens to land exactly on the root, so its relative criterion fires and it reports Success. Same answer, different retcode — a termination artifact, not a wiring bug.

Fix: set an explicit abstol=1e-9 default (the _SOLVE_DEFAULTS constant in src/compile/solve.jl). With this default, both storage paths report Success in 6 steps on the canonical nonlinear benchmarks (Broyden tridiagonal n=30, Powell badly scaled, extended Rosenbrock n=30). A real stall leaves a residual far above abstol and is still reported — the fix makes the retcode truthful without masking genuine failures.

5.3 Key finding: the probe found a real failure (+ memory bound now proven)

The inference cliff (and the original ~80 GB verify event)

The scalability probe (benchmark/scaling_probe.jl) was built to answer "does the architecture scale beyond the 29-row turbojet?" — and it found two genuine defects. (1) The original kernel dispatch used recursive tuple unrolling (Base.tail). Julia's inference abandons specialization of deep tuple recursion past a few tens of elements, falling back to dynamic dispatch. The cliff hit at exactly 42 rows: 270,000 allocations per call at 102 rows. (2) The original verify_sparsity built a dense N×N Jacobian to cross-check sparsity. At 1,002 variables this requires a ~1,002×1,002 dense Float64 matrix evaluated at every ForwardDiff seed — roughly 1,002 full-Jacobian evaluations — which consumed approximately 80 GB of memory and OOM-died. This was a real failure: the approach did not scale. It has been replaced with a row-by-row verifier (bounded per-row ForwardDiff chunks → no dense N², no OOM). The current measured peak RSS is 0.61 GB @ 1,002 rows / 0.60 GB @ 5,002 rows in fresh processes — both confirming the fix is complete.

The fix — same day

@generated straight-line dispatch (no recursion depth → type-stable at thousands of rows) plus row-by-row sparsity verification (bounded per-row ForwardDiff chunks → no dense N², no OOM). Same guarantee preserved: every numerically nonzero (row, col) must be declared.

src/compile/residual.jl — the @generated straight-line emitter (verbatim)

@generated function _eval_rows!(F, x, kernels::Tuple, dep_cols::Tuple, p, i0)
    n = length(kernels.parameters)
    body = Expr(:block)
    for i in 1:n
        push!(body.args, :(@inbounds F[i0 - 1 + $i] =
            kernels[$i](_gather(x, dep_cols[$i]), p)))
    end
    push!(body.args, :(return nothing))
    return body
end

Limitation: codegen first-call latency

The @generated straight-line emission has a one-time first-call compilation cost at large N: ~1.7 s at 1,000 rows, ~14.5 s at 5,000 rows. This is amortized over sweeps and optimization runs (a single solve is sub-10 ms even at 5,002 rows). It is a real cost, stated plainly — and a candidate for the ADR-0005 MTK ledger (MTK's codegen has the same trade).

The story: the probe was designed to find exactly this — before a turbofan did

A 3-spool turbofan multi-point stack is hundreds of rows; the recursive unroll would have silently degraded it. The probe surfaced the cliff in synthetic ducts first. A red-first regression test now pins it — the captured live failure before the fix:

commit 2054d53: "Red-first regression: test/compile/test_scaling_alloc.jl (200-row chain, captured live 1117808-alloc failure before fix)". The test now asserts @allocated residual! == 0 and @allocated jacobian! == 0 at 200 rows, and that verify_sparsity completes at that scale.

TSFC gate miss — characterized model limitation, not a hidden error

The +12.4% TSFC gap is prominently stated here because it is the headline result of the P7 gate. It is not buried in a footnote. The gate miss has a single, well-characterized cause:

  • TSFC ∝ FAR at fixed Fn (thrust matches exactly, so TSFC = ṁfuel/Fn = FAR × ṁair/Fn). Our FAR = 0.0334 (referenced at 298.15 K) vs PyCycle CEA FAR = 0.0297 — a ~12% fuel-flow difference.
  • Root cause: constant hot-gas cp. CEA's mass-averaged products cp rises through combustion, and dissociation absorbs energy; both effects mean CEA requires less fuel to reach the same Tt4. The CPG two-gamma model's fixed cp,hot=1239 J/kg·K cannot capture this.
  • All non-physical causes excluded: units (TSFC conversion factor 2.8325×10⁻⁵ derived and recorded), matching table (freestream T0/P0 reproduce ISA to 4 sig figs; Fn matches exactly), ηmech placement (shaft.fracLoss=0.01 confirmed).
  • Alignment attempt rejected on scientific grounds: lowering cp,hot toward 1150 J/kg·K within ADR-0001's [1150, 1250] range reduces FAR to ~0.0318 (TSFC gap ~7%), but simultaneously worsens Tt5 agreement (1346 K vs CEA 1374 K; our current value 1365 K at cp=1239 is closer). No single constant cp matches both FAR and turbine expansion — exactly the variable-cp coupling this ADR defers to IdealGasThermo.jl. We kept cp,hot=1239 (best turbine-side and Tt/Pt agreement) and did not tune to the gate.

Resolution path: TSFC ≤10% is the first IdealGasThermo (TPG) deliverable post-v0.1. The gate test asserts the 8 station Tt/Pt scalars at ≤10% (binding PRD quantities, all pass) and pins TSFC against the reference with the documented model-gap band (≤15%, measured 12.4% after the 298.15 K reference correction).

6.3 Timing comparison — same design-point solve, three backends

A fair three-way wall-clock comparison of the same matched solve (single-spool turbojet, 35 kft / M0.8, πc=12, Tt4=1600 K, Fn=50 kN balances) across three backends: PyCycle with CEA real-gas thermo, PyCycle with TABULAR (JetA table) thermo, and PowerCycles.jl v0.1.0. The PyCycle TABULAR backend is invoked by setting Cycle.options['thermo_method']='TABULAR' and thermo_data=pyc.AIR_JETA_TAB_SPEC (the pickled JetA table) at the cycle level — these propagate to every element automatically — and naming the combustor fuel reactant 'FAR' (the tabular composition key) rather than a CEA fuel string. The invocation was confirmed against the installed pyCycle 4.4.0 source, not guessed.

TABULAR vs CEA agreement. What each phase includes. A (build): model construction only — for PyCycle, om.Problem() + cycle build + prob.setup(check=False); for PowerCycles, turbojet_manifest + validate! + compile(verify=false). B (first solve): the first design solve in a fresh process. For PyCycle this is the first run_model(), which includes OpenMDAO's first-call solver setup and lazy thermo-table load. For PowerCycles this includes Julia's first-call JIT/codegen of residual!/jacobian! and the NonlinearSolve path — the dominant cost, by design (see §5 codegen latency). C (warm re-solve): after perturbing the runtime target Fn 50→51 kN, re-solve in the same warm process; PyCycle changes the balance RHS and calls run_model() again, PowerCycles reuses the init_solve cache via solve_program!. Five iterations, median reported. End-to-end process wall is the full shell real time of one cold run — the "time to first answer" a user feels, including interpreter/runtime startup and package/import load.

Methodology and fairness caveat. All timings are wall-clock on a single machine (PyCycle via Python time.perf_counter, PowerCycles via time_ns; medians over the warm loop). The comparison is not apples-to-apples in an absolute sense: the PyCycle/OpenMDAO timings carry Python + framework dispatch overhead on every solve, while the PowerCycles phase B carries Julia's one-time JIT cost (amortized to zero on every subsequent solve). The TABULAR backend is PyCycle's faster mode and the fairer steady-state baseline. Once compiled, PowerCycles' warm re-solve (~54 µs; pure-compute min ~70 µs in this harness) is roughly three orders of magnitude faster than PyCycle's warm re-solve, reflecting compiled straight-line kernels with a fixed sparse Jacobian versus framework-mediated component execution. What this does and does not claim: it is a single design point on one machine, reported to show the cost structure (one-time build/JIT versus per-solve warm cost) — not a general engine-modeling benchmark, and not a statement about either tool's behavior on larger cycles, off-design sweeps, or other hardware.

examples/sweep_pressure_ratio.jl — 5 πc points using the warm-sweep API (verbatim excerpt)

m = turbojet_manifest(; pi_c=12.0, Tt4_target=1600.0, Fn_target=50_000.0)
prog = compile(validate!(m); verify=false)
p0 = turbojet_params(; pi_c=12.0, Tt4_target=1600.0, Fn_target=50_000.0)
cache = init_solve(prog, p0)
for Fn in 40_000.0:5_000.0:60_000.0
    p = turbojet_params(; pi_c=12.0, Tt4_target=1600.0, Fn_target=Fn)
    sol = solve_program!(cache, prog, p)
    res = TurbojetResult(prog, sol, p)
    @printf("  %-12.0f  %-12.4e  %-10s\n", Fn, tsfc(res), res.converged)
end

res.converged is reported at every point — convergence is never assumed. The warm-sweep API (init_solve + solve_program!) eliminates per-point solver-cache reconstruction for runtime-param sweeps (~3× cheaper per point).

7.c Authoring a component NOW — the afterburner test case

The acid test for "is authoring ergonomic": a NEW component authored from docs alone (zero source-reading), 38 lines, hand-values matched to 1e-8.

examples/author_afterburner.jl — manifest core (verbatim)

function afterburner_manifest(hot::CPGGas; owner=:afterburner)
    m = AssemblyManifest()
    push!(m, VariableSpec(:Tt_in;   unit=:K,            nominal=1365.0, owner=owner))
    ...
    push!(m, VariableSpec(:FAR_ab;  unit=:dimensionless,nominal=0.02, scale=0.02, owner=owner))

    # Pressure loss: Pt_out = pi_ab * Pt_in
    push!(m, ResidualRowSpec(:ab_Pt; owner=owner, units=:Pa, scale=1e5,
        deps=[:Pt_out,:Pt_in], derivative=:forwarddiff, f=(d,p)->d[1]-p.pi_ab*d[2]))
    # Energy balance: FAR_ab*(eta_b*LHV - h_out) = h_out - h_in
    push!(m, ResidualRowSpec(:ab_FAR; owner=owner, units=:dimensionless, scale=0.02,
        deps=[:FAR_ab,:Tt_out,:Tt_in], derivative=:forwarddiff,
        f=(d,p)-> d[1]*(p.eta_b*p.LHV - h_of_T(p.hot, d[2]))
                  - (h_of_T(p.hot, d[2]) - h_of_T(p.hot, d[3]))))
    return m
end

All hand values match.

The authoring contract

  • Write a kernel f(deps, p); deps is the sparsity declaration — no separate pattern to maintain.
  • validate! names your mistakes: a dep that points at nothing raises DanglingDepError.
  • KernelArityError now catches arity slips with the row name: "row :ab_FAR kernel indexed beyond its 3 declared deps — add the missing dep."

Trust: how correctness is enforced

TDD ladder with red-evidence discipline

Red–green–refactor per phase; cycle logs must include per-cycle red-failure evidence lines. Protocol note: P3 slipped to one-pass implementation (module written in one go). The slip was caught, called out in HANDOFF, and the enforcement tightened — P4+ require one-test-one-impl with logged red evidence, and the skill-reading mandate worked from P5 on.

Two-oracle derivative testing

Analytic derivatives match ForwardDiff to rtol 1e-10 for every thermo function, both gases. The composition test uses two independent oracles — hand chain-rule and central finite difference — and was teeth-checked: deliberately dropping a chain-rule factor produced 3 failures, proving the test can fail.

Salvaged-fixture provenance

Compressor fixtures mined from the old repo with provenance comments. Finding: the inverse case is η=0.84 (the old file won over the briefed 0.86) — recorded rather than silently reconciled. Both pass the full manifest→validate!→compile(verify=true)→solve path; inverse recovers PR=11.

Spec-governed components

The 29×29 squareness ledger (physics doc §5) is pinned in-test: the assembly asserts n_rows == n_unknowns == 29. Component code is the single source of physics — the assembly reuses the same push_*_rows! helpers the standalone unit tests use.
